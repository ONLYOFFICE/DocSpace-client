# Design

## Context

See proposal.md for motivation. Both apps run the same order. The client invite panel (`packages/client/src/components/panels/InvitePanel/index.js`) sends `api.rooms.setRoomSecurity` for every invitee at line 473, closes the panel and then calls the shared `rewrapForInvitedMembers` (`packages/shared/services/private-room/room-member-flows.ts`), which runs `addMembersToEncryptedRoom`, turns skipped members and partial failures into notices the panel shows as toasts, and starts the backfill without awaiting it. The SDK private invite panel (`packages/sdk/src/app/(private)/_components/invite-panel`, around the generic `packages/sdk/src/app/(rooms)/_components/invite-panel/index.tsx`) unlocks through `onBeforeSubmit`, sends the security update at line 651, closes, and hands the members to `usePrivateInviteFlow`, which calls the same shared function. Neither verifies the invitees before the grant: the shared service (`packages/shared/services/private-room/room-encryption.ts`) checks each member's key against the TOFU pin inside `addMembersToEncryptedRoom`, after it, and returns per-member and per-file results; `validateMembersForEncryption` runs the same check on its own. Both take the keys from the room access keys, which the server collects for the room's members only (`EncryptionKeyPairDtoHelper.GetKeyPairForRoomAsync`, `products/ASC.Files/Core/Core/Entries/EncryptionKeyPairDto.cs:245-296`, through `fileSharing.GetSharedInfoAsync`), and no route returns the public key of a user who is not a member yet, so before the grant neither sees an invitee's key. The member-removal guard counts uploads whose `toFolderId` equals the room id (`packages/shared/utils/uploadErrors.ts:125-132`, reached from `Members/sub-components/User.tsx:176` through the upload store's `getActiveUploadCountForRoom`).

The SDK's upload items carry only the target folder id (`packages/sdk/src/app/(docspace)/_store/UploadStore.tsx:47-51`), and its removal guard passes that id to the counter as `toFolderId` (`packages/sdk/src/app/(private)/_store/PrivateEncryptedUploadStore.tsx:131`), so a counter matching on the room id counts nothing in the SDK until its items carry it.

The stashed `V1_RELEASE_PROGRESS.md` (edge case #65) documents the root-only upload guard as a deliberate "FE-only mitigation" and says deep hierarchies are rare; it does not document the grant-before-wrap order at all. `AUDIT_BACKEND.md` lists "BH-1 / P0 invite" as closed on the server side (the security split), which is why the client-side order is the remaining gap.

Server constraints that bound the ordering (`../server` on `hotfix/v4.0.1`):

- Writing access entries (`PUT files/{fileId}/access`, `FileStorageService.SetEncryptionInfoAsync`, `products/ASC.Files/Core/Core/FileStorageService.cs:5268-5276`) checks read access of every *subject* user named in the body (`fileSecurity.CanReadAsync(file, k.UserId)`) and throws before storing anything if one fails. An invitee who is not yet a room member cannot read the room's files, so a wrap for them is refused, and the refusal rejects the whole request, including the entries for other users in it.
- No server path removes a user's access entries: the only delete (`DeleteFileKeysAsync`, `products/ASC.Files/Core/Core/EF/Queries/AbstractQueries.cs:116`) is called only from `FileDao.SetFileKey` (`products/ASC.Files/Core/Core/Dao/TeamlabDao/FileDao.cs:2404`), which replaces the rows of the users listed in the request. Removing a member leaves their entries in place.
- Granting a private room to an invitee who never registered a key is refused by the server (`products/ASC.Files/Core/Utils/FileSharing.cs:263-266`, `ThrowIfKeysAreNotSetAsync` on the invitee from line 129). A user who registered keys and later deleted all of them still has a (now empty) key record and passes the check. The check throws inside the per-invitee loop, and each earlier invitee's share is stored in its own iteration (`fileSecurity.ShareAsync`, line 395), so the request fails at that invitee while invitees processed before it may already be members.

## Goals / Non-Goals

**Goals:**
- A newly granted member can always read every file that existed at grant time, or is visibly flagged as pending.
- Skipped invitees never become members silently.
- The upload guard reflects every upload the device is making into the room.

**Non-Goals:**
- Implementing server-side changes in this change (any server option from decision 1 is tracked in `private-rooms-server-hardening`).
- Re-keying on removal, cross-device races.

## Decisions

1. **Grant first, then wrap (decided 2026-10-26).** The client sends the room security update for the verified invitees only and then wraps every encrypted file for those it granted; if the security update fails, no wrap is written. The verification of the invitees moves before the grant, into a step of the shared membership flows that both invite panels call. It reads the invitees' keys from the route `private-rooms-server-hardening` adds for this (requirement "Public keys of prospective members", decided 2026-10-28), since the room access keys cover members only. A partial wrap result shows as the pending-access state with a retry (decision 2), and the backfill sweep re-wraps for every member when a room manager opens the room. The originally proposed client-side reorder (wrap first, then grant) cannot work against today's server: the access-entry write refuses entries for users who cannot read the file, and an invitee cannot read it until the security update has granted them the room (see Context). Alternatives: (b) wrap-first after a server change that accepts entries for invitees named in a pending grant, not taken because it needs a new authorization concept on the server; (c) a server endpoint that accepts `{ invitees, fileKeys[] }` and writes the grant and the entries in one transaction, the later target, recorded in `private-rooms-server-hardening` and not a release prerequisite.
2. **Pending-access state lives on the client, keyed by member and room.** The shared invite re-wrap (`rewrapForInvitedMembers`) records `{ roomId, userId, missingFileIds }` after a partial failure, and `missingFileIds: "all"` for every invitee when the re-wrap fails as a whole (decided 2026-10-28: such a failure leaves no list of the files each invitee misses), in a MobX store in `packages/shared/services/private-room` that both apps read (decided 2026-10-28: the client has no Members store, its member list being local state of the Members view, and one record serves the client Members view and the SDK private members list alike); the Members view renders Common:EncryptedAccessPending and a retry item that re-runs the wrap for `missingFileIds`, or for every encrypted file of the room when the record says `"all"`. The retry takes a stored write as its confirmation and clears the record once every write was stored (decided 2026-10-28): the server reads back a user's own file keys only (`FilesController.GetEncryptionInfoAsync`, `products/ASC.Files/Server/Api/FilesController.cs:1229-1251`, through `FileDao.GetFileKeys`, which filters on the caller, `products/ASC.Files/Core/Core/Dao/TeamlabDao/FileDao.cs:2434-2446`), no other route reads the file keys table, and the write (`FileStorageService.SetEncryptionInfoAsync`, `products/ASC.Files/Core/Core/FileStorageService.cs:5242-5277`) checks every recipient before it stores the entries of one file in a single transaction, so a write that succeeds has stored them all. An upload that leaves a member out because the user refused their changed key adds that file to the same record (decided 2026-10-28), so the Members view shows such a member as pending too, and once the user trusts the key anywhere, the shared encryption provider runs the retry for that member in every room they are recorded for (task 3.3). The record lives in memory for the page session: after a reload it is gone and the backfill sweep is the fallback, as befits a hint. Alternatives: derive the state on every Members load by diffing file access lists against the member list, not possible because the server does not read back another member's file keys (see above); a separate record in each app, rejected as two copies of one state; persisting the record in localStorage, not taken because the record is a hint that the backfill sweep stands behind.
3. **Skipped invitees stay in the panel.** Instead of closing on send, the panel shows the result list (granted / pending / skipped with reason) and closes on an explicit button; this is what the SDK parity plan called "F-6 invite re-encrypt progress terminal". Alternative: keep the toasts. Rejected because the toasts are the current, insufficient behaviour. The SDK private invite panel shows the same result view, replacing the close after the security update that `private-rooms-sdk-client-parity` 5.3 gives it. The view (decided 2026-10-28) lists the granted invitees, the pending ones with the count of files they miss, and the skipped ones with their reason, and offers "Invite again", which returns to the invitation form holding only the skipped invitees, next to "Close".
4. **Upload guard uses the room membership of the target folder.** `countActiveUploadsForRoom` receives the room id of each queued item (captured at upload start, the same way `encryptionRoomId` already is) and counts matches regardless of folder depth. Alternative: walk the navigation path per item. Rejected: the id is already captured at start. SDK upload items get the room id when they are queued, from the private room page that already passes it to the orchestrator as the encryption room, and the SDK counter adapter passes it on.

## Risks / Trade-offs

- [Grant first leaves a window in which a granted member has no entries] → the pending-access marker and retry make it visible, and the backfill sweep closes it on a room manager's next visit; the transactional endpoint (c) would close it on the server.
- [An invitee who never registered a key makes the server fail the security update at that invitee, after earlier invitees may already have been added] → the client must leave skipped invitees out of the request in every option.
- [Pending state is per device and per page session] → another device or a reload does not see the marker, and no device can read another member's file keys to rebuild it; the backfill sweep re-wraps for every member when a room manager opens the room, and the transactional grant-and-keys endpoint (c) would remove the gap.
- [Changing the panel close behaviour affects the non-private invite flow] → the result view is rendered only for private rooms; the non-private branch keeps the current close.
- [Sequencing with `private-rooms-sdk-client-parity`] → resolved: that change was archived on 2026-10-28 with its 5.1 (shared re-wrap) and 5.3 (SDK invite panel) done, so the requirements this sdk-surface delta modifies and renames are in the main spec.

## Migration Plan

No data migration. Behind the `privateRooms` flag. Rollback by revert.
