# Internationalization (i18n)

For bulk translation work use the `translate-locales` skill; for a single key
use `translate-key`; for coverage reports use `translate-progress`; to find keys
whose English moved while the translations did not, use `translate-stale`. This
rule is the reference for where files live and what the tests enforce.

## Locale file locations

| Namespace | Locale files |
|-----------|-------------|
| `Common` | `public/locales/{lang}/Common.json` |
| `ChangeLinkTypeDialog`, `CompletedForm`, `DeepLink`, `Editor` | `packages/doceditor/public/locales/{lang}/{Namespace}.json` |
| `Confirm`, `Consent`, `Errors`, `Login`, `TenantList`, `Wizard` | `packages/login/public/locales/{lang}/{Namespace}.json` |
| `Management` | `packages/management/public/locales/{lang}/Management.json` |
| *everything else* | `packages/client/public/locales/{lang}/{Namespace}.json` |

Meta files (translator context + code usage examples) live at the same path under `.meta/{Namespace}/{Key}.json`.

## Brand names, constants and culture labels

`public/locales/.constants/` holds three locale-independent JSON files. They are excluded from translation linting and must **never** be accessed via `t()` — each has its own getter:

| File | Content | Getter | Import |
|------|---------|--------|--------|
| `brands.json` | Product/brand names (`DocSpace`, `ONLYOFFICE`, …) | `getBrandName(key)` | `@docspace/shared/constants/brands` |
| `consts.json` | Technical abbreviations (`LDAP`, `PDF`, `OCR`, `BETA`, …) | `getConstName(key)` | `@docspace/shared/constants/consts` |
| `cultures.json` | Language display names in native script (`Русский`, `Deutsch`, …) | `getCultureLabel(code)` | `@docspace/shared/constants/cultures` |

Per-language overrides use a `-{lang}` suffix inside the JSON (e.g. `"OCR-ru": "Распознавание текста"`).

**Never hardcode brand names** in translation strings. Pass them as `{{variables}}`:

```tsx
import { getBrandName } from "@docspace/shared/constants/brands";
import { getConstName } from "@docspace/shared/constants/consts";

t("Common:SomeKey", { productName: getBrandName("ProductName") })
```

```json
"SomeKey": "Expand your {{productName}} with premium modules"
```

## Translation tests

Run after any locale changes:

```bash
cd common/tests && npx vitest run test/locales.test.js
```

Key rules the tests enforce:
- All locale JSON files must use raw UTF-8 characters, **not** `\uXXXX` escape sequences (e.g. write Cyrillic directly, not `к`). This happens when writing JSON with Python's `json.dumps()` without `ensure_ascii=False`.
- Translation strings must not contain hardcoded brand names (`ONLYOFFICE`, `DOCSPACE`). Use `{{productName}}` variables passed via `getBrandName()`.
- Non-English locales must not be identical copies of English for long strings.
- `sr-Cyrl-RS` must use Cyrillic script exclusively (never Latin).

### Structural checks on translated values

These exist because a bulk term rename damaged values in ways the older tests
did not notice. Each one is comparative where English is the reference, so a
quirk that English itself has is not reported.

| Test | What fails |
|------|-----------|
| `NewlineConsistencyTest` | a value has a different number of `\n` than English — `\n` is deliberate paragraph structure, so a lost one collapses two paragraphs and an extra one splits a sentence |
| `LlmArtefactsTest` | machine-translation wrapper reached the JSON: a ` ``` ` fence, the whole value wrapped in `"…"`, a raw `{"…` object, or a refusal sentence |
| `DoubleSpaceTest` | repeated spaces inside a value (`"  |  "` in the tariff strings is the one exception) |
| `SpaceBeforePunctuationTest` | a space before `. , : ; ! ? )` that English does not have — the tell-tale of a deleted placeholder whose space stayed behind. French legitimately spaces `: ; ! ?` and is exempt for those |
| `MissingSpaceAfterSentenceTest` | a sentence glued to the next (`"…uroven.Oni…"`). Scripts that do not space sentences (`zh-CN`, `ja-JP`, `ko-KR`, `lo-LA`, `si`, `ar-SA`) are exempt |
| `FinnishCaseSuffixTest` | Finnish attaches a case ending with a colon to an ordinary lowercase word (`"työtila :een"`) — that convention only applies to names and abbreviations (`LDAP:n`), so the word itself must be inflected (`"työtilaan"`) |

All six run with **no allowlist** — the inherited debt they first exposed (98
strings) was fixed rather than frozen, so any hit is a new regression. Do not
introduce an allowlist to make one of them pass.

### Duplicate English values

`DuplicateEnValuesTest` fails when two keys in the **same namespace** hold the
same English value: the UI then ships one wording under two names and every
language pays to translate it twice. It is what catches a rename that lands on
an existing string — `FormSetTitle` "Form Set" → "Form space" next to
`FormSpaceTitle` was invisible to `FullEnDublicatesTest`, which groups by
key *and* value and so only sees one key repeated across namespaces.

Unlike the six checks above this one **does** carry a baseline,
`common/tests/test/duplicate-en-values-allowlist.json`, because its inherited
debt (46 groups) is mostly deliberate — `AiSuggestions` reuses one prompt for
several sections, `Common:Label`/`Common:Name` are separate UI concepts. An
entry is the signature `Namespace: KeyA, KeyB` with the keys sorted, so a
third key joining an allowlisted pair changes the signature and still fails.
The list must only ever shrink; `StaleDuplicateEnValuesAllowlist` fails on
entries that no longer collide, so a fix and its baseline removal have to land
in the same commit.

Prefer merging the keys over extending the baseline: keep one, point its
callers at it, delete the rest from every language. Add a signature only when
both keys genuinely have to stay. Known debt to unwind first:
`Common: FormRoom, FormSetTitle, FormSpaceTitle`, all three "Form space" —
`FormSetTitle` cannot go until `libs/ui-kit/components/room-type/RoomType.utils.ts`
switches to `FormSpaceTitle` in the ui-kit repo.

Cross-namespace duplicates are **not** enforced (116 groups today); a Common
key and a Files key holding the same text is usually a namespace re-declaring
something Common already offers, but too many are legitimate to gate on now.

Each check compares like with like before reporting, and getting that
normalisation right matters more than the pattern itself: replace
`{{placeholders}}`, URLs, ellipses and file extensions with a **lowercase**
stand-in rather than deleting them (deleting `" .xlsx."` manufactures `" ."`,
and an upper-case stand-in suppresses real hits because a capital before a
period reads as an abbreviation), keep the abbreviation exception Unicode-aware
(`(?<![\p{Lu}0-9])`, or Cyrillic `В.{{version}}` is misread while Latin
`V.{{version}}` is not), and treat `<br>` and a closing-tag/opening-tag junction
as sentence separators while dropping purely inline markup.

## Restructuring an English string other locales already have

`WrongTranslationVariablesTest` and `WrongTranslationTagsTest` compare English
against every other language and fail when the counts differ. Both skip a key
whose value is missing or empty in the other language (`if (!lngKey ||
!lngKey.value) return`), so a key that does not exist elsewhere is not their
concern — only a key that is **present but structurally stale** is.

That is exactly what an edit to an already-translated string produces: rewrite
it into a `Trans` component or add a `{{variable}}`, and English now carries N
tags/variables while the other 31 locales still hold the old plain sentence
with none. Both tests run on pre-push, so the push is blocked.

The fix is to **delete the whole key from the non-English files** — not to
translate the new wording, and not to leave the old value in place. The key
falls back to English until the translation department retranslates it, and the
old value was wrong already: it lacked the new content. Delete the key rather
than blanking it to `""`, which only trades these two failures for
`EmptyValueKeysTest`.

Leave `.meta/{Namespace}/{Key}.json` alone. `content_en_sha1_hash` is the sha1
of the English `content`, and
`common/translation-app/backend/src/scripts/generate-metadata.js` treats a hash
mismatch as "source changed, needs re-review" — that stale hash is the
pipeline's only signal. Hand-updating it silently marks the new wording as
already reviewed.

The mirror case is **not** caught by anything: change only the *words* and the
counts still match, so 31 locales can keep the previous wording through a green
pre-push run. The stale `content_en_sha1_hash` in `.meta` is the sole signal,
and `generate-metadata` erases it. The `translate-stale` skill
(`.claude/scripts/audit/stale-translations.mjs`) is what finds those keys.

## Translation completeness

Three tests report keys that exist for `en` but not for another language:

| Test | Scope | npm script |
|------|-------|------------|
| `NotTranslatedOnBaseLanguages` | base languages only | `test:only-base-languages` |
| `NotTranslatedOnAllLanguages` | every language folder | `test:only-all-languages` |
| `MissingLocaleFilesTest` | namespace files absent for a language | — |

The last two are covered by `test:only-missing-keys`. All three are skipped on
pre-push (`test:lefthook` sets `SKIP_BASE_LANGUAGES_TEST` and
`SKIP_ALL_LANGUAGES_TEST`), so pending translation work does not block a push —
**a green pre-push run does not mean the locales are complete.**

The same data as a report, with the concrete key list:

```bash
node common/scripts/translation-stats.js --no-meta --missing
```

`libs/ui-kit/locales/` is out of scope for both the tests and the stats script —
the ui-kit is a git submodule, so its gaps must be fixed in
`docspace-ui-kit-react`.
