Refuse a group in a private room by a rule of its own, with its own reason. Verify: server tests in `products/ASC.Files/Tests/Tests/08_Private` for a member with an empty key set who leaves, is removed and gets another role without a 403, for an owner change by an owner without keys, and for a group refused with a reason other than the missing keys; on the stand, the leave of a member without keys
- [ ] 1.2 Backend: give a refusal caused by missing keys a stable reason, a code or an error type the client can rely on, distinct from a refusal by access rights (`ResponseWrapper`, `common/ASC.Api.Core/Middleware/ResponseWrapper.cs`, answers both as 403 with a message). Verify: a server test reads the reason from the answer of a refused invitation of a user without keys, and does not find it in a refusal by rights
- [ ] 1.3 Backend: make the per-file key listing follow the room. `EncryptionKeyPairDtoHelper.GetKeyPairAsync(fileId)` (`products/ASC.Files/Core/Core/Entries/EncryptionKeyPairDto.cs`) answers the users with a share record of their own and the file's creator: the room owner is missing for a file another member created, and a creator who left the room stays. The route is the one proposed for the desktop bridge in `private-rooms-remove-dead-api-calls` 2.0. Verify: server tests for a file uploaded by a member, whose listing holds the owner's keys, and for a file whose creator left, whose listing does not hold the creator's
- [ ] 1.4 Backend: do not leave a private room with an owner who cannot open its files when the rooms of a deleted user are reassigned. `FileStorageService.ReassignRoomsAsync` updates the creator of every room in one statement (`FolderQueries.ReassignRoomsAsync`) and skips the key check of an owner change. Verify: a server test reassigns a private room to a user without keys and states the outcome, which leaves no private room owned by that user
- [ ] 1.5 Backend: answer what happens to the stored key pair of a user who is turned into a guest, and whether such a guest passes the key check of 1.1. Verify: the answer is recorded in design.md with its date, and a task is added here if a behaviour is asked

## 2. Listing and rights

- [ ] 2.1 Backend: leave private rooms out of the Forms and form-template areas. `SearchAreaExtensions.MatchesRoom` (`products/ASC.Files/Core/Core/VirtualRooms/SearchArea.cs`) admits every form-filling room there, private or not. The refusal of the private flag on a form-filling room at creation is `private-rooms-server-hardening` 12.8. Verify: a server test lists the Forms area of a portal holding a private form-filling room and does not find it
- [ ] 2.2 Backend: report as false the rights of operations that do not work on encrypted content. In `FileSecurity.FilterEntryAsync` (`products/ASC.Files/Core/Core/Security/FileSecurity.cs`) the owner of a private room is granted Rename, ReadHistory, EditHistory, Lock, CopyLink, CustomFilter and SubmitToFormGallery on a file, and `CanUseAi` on the room, because the private-room refusals stop short of them; `FileStorageService.UpdateCommentAsync` then stores a version comment of an encrypted file in the clear. Comment and Review stay granted (design decision 3, for the owner to confirm). Verify: a server test reads these seven rights as false for an encrypted file and `CanUseAi` as false for a private room, as the room owner, and gets a refusal for a version comment of an encrypted file
- [ ] 2.3 Backend: answer the title of the private section root in the culture of the calling user; on the stand it came as "Private" for a Russian user. The labels `PrivateRoomTitle` and `PrivateFolderTitle` of the letters are `private-rooms-server-hardening` 4.5. Verify: a server test requests the root folders as a user of another culture and reads the translated title
- [ ] 2.4 Backend: answer which routes the switched-off E2E rooms app closes. Today `IsPrivateRoomsAppEnabledAsync` (`products/ASC.Files/Server/Api/FoldersController.cs`) guards the private section listing and the root list only; the rooms list with the private area or the private filter, the key routes and the creation of a private room work with the app off. The owner decided on 2026-11-06 that private rooms are hidden then. Verify: the answer is recorded in design.md with its date, and the main spec requirement "The E2E rooms app gates only the private section listing" is revised by a delta here if the behaviour changes
